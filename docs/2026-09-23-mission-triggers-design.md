# 任務觸發系統設計建議：時間驅動 × 事件驅動

2026-09-23 · 提案，尚未實作

## 0. 一句話

把「**任務（做什麼）**」和「**規則（什麼時候、為什麼做）**」拆開。任務是可重複使用的範本；規則負責在時間到或事件發生時啟動任務，並決定優先級、要不要人確認、冷卻多久、撞到別的任務怎麼辦。

現在的 `Mission.trigger` 是一對一綁死的：一個任務只能有一個觸發條件，也沒有辦法表達「晚上 22:00 巡一圈，**而且**偵測到人員時去看一下」。

---

## 1. 為什麼要拆開

| 現在 | 問題 |
| --- | --- |
| 一個任務一個觸發條件 | 同一條巡邏路線要在不同時段、或因不同事件執行，就得複製好幾份任務，改路線時要改好幾份 |
| 事件觸發只能跑固定路線 | 事件是有位置的（「南走廊偵測到人員」），固定路線去不到事件發生的地方 |
| 沒有優先級與搶佔 | 巡邏中偵測到入侵時，狗不知道要不要放下巡邏去處理 |
| 沒有冷卻與去重 | AI 同一個人連續偵測 20 次，就會觸發 20 次 |
| 誤報沒有緩衝 | AI 誤判一次，狗就自己跑去廣播「此區域禁止進入」 |

業界的做法相同：Boston Dynamics Spot 的 Scout / Orbit 把「Mission」和「Schedule」分開管理；Cobalt、Knightscope 這類保全機器人都有獨立的「事件回應（event response）」流程；Home Assistant、AWS IoT Events 也都是「觸發 → 條件 → 動作」的規則模型。

## 2. 資料模型

```ts
/** 做什麼：可重複使用的範本 */
Mission {
  id, name
  target: FixedRoute { waypoints[] }           // 固定巡邏路線
        | EventLocation { radiusM, lookAt }    // 前往事件發生的位置（事件驅動專用）
        | Zone { zoneId, pattern: "sweep" | "perimeter" }
  actions: Action[]                            // 到點後做什麼（快照、熱像、廣播、plugin…）
  estimate: { sec, batteryPct }                // 狗端估算
}

/** 什麼時候、為什麼做 */
Rule {
  id, name, enabled
  trigger: TimeTrigger | EventTrigger
  missionId
  priority: 0 | 1 | 2 | 3            // 0 緊急 · 1 事件回應 · 2 例行巡邏 · 3 維護
  mode: "auto" | "confirm" | "notify"
  confirm?: { timeoutSec, onTimeout: "run" | "cancel" }
  guards: { minBattery, allowedStates[], requiresFeature }   // 啟動前必須成立的條件
  throttle: { cooldownSec, maxPerHour, dedupeBy: "zone" | "track" | "none" }
  conflict: {
    preempt: "never" | "lower_priority"                 // 能不能打斷正在跑的任務
    onPreempted: "resume" | "restart" | "drop"          // 被打斷的任務之後怎麼處理
    queueTtlSec                                         // 排隊多久就過期（事件回應太晚到就沒意義了）
  }
  followUp?: { onSuccess?: ruleId, onFail?: ruleId, escalate?: Escalation }
}

TimeTrigger {
  kind: "time"
  schedule: Once { at } | Recurring { rrule, tz }   // RFC 5545 RRULE：每日、每週、每月第 N 個週幾
  window?: { from: "22:00", to: "06:00" }           // 「每 30 分鐘，但只在這個時段內」
  jitterMin?: number                                // 隨機偏移（見 §3.3）
  exceptions?: DateRange[]                          // 假日、施工、活動
  missed: { policy: "skip" | "catch_up", graceMin } // 狗在那個時間點不能跑時怎麼辦
}

EventTrigger {
  kind: "event"
  source: "ai" | "system" | "sensor" | "plugin" | "external"
  type: string                    // person / intrusion / fire / fall / gas_high / door_open / fence_breach …
  filter: {
    zones?: zoneId[]
    minConfidence?: number        // AI 信心分數下限，例如 0.8
    classes?: string[]
    activeWindow?: { from, to }   // 只有夜間生效
    persistSec?: number           // 持續存在 N 秒才算（濾掉路過的誤報）
    countWithin?: { n, sec }      // N 秒內出現 M 次才算
  }
}

Run { …, cause: { ruleId, kind, eventId?, scheduledAt?, confirmedBy? } }  // 每次執行都記錄「為什麼跑」
```

## 3. 時間驅動：專業做法

### 3.1 用 RRULE，不要自己發明格式
「每週一、四」「每月第一個週五」「每天 22:00–06:00 每 45 分鐘」都能用 RFC 5545 RRULE 表達。UI 繼續用視覺化選擇器，底層統一存成 RRULE，未來接行事曆、Portal 都不用轉換。

### 3.2 時段 + 間隔，比固定時間更符合保全需求
保全真正的需求通常是「**夜間時段內每 N 分鐘巡一次**」，而不是「22:00、23:00、00:00…」這樣逐一列出。

### 3.3 刻意加入隨機偏移（jitter）—— 保全領域的特殊需求
固定時間巡邏會被摸清規律：有心人只要等狗走過就安全了。可以設定 ±N 分鐘的隨機偏移，或在幾條路線之間輪替，讓巡邏時間不可預測。這是一般排程系統不需要、保全系統卻必須有的功能。

### 3.4 錯過的排程要有明確規則
狗在排程時間可能正在充電、E-Stop、故障，或正在跑別的任務：
- `skip`：直接跳過，記錄「因為 X 跳過」
- `catch_up`：在寬限時間內補跑，超過就放棄

**不要**讓它默默消失；列表上要看得到「上次：跳過（電量不足）」。

### 3.5 例外日與時區
- 假日、施工、大型活動期間要能暫停或換成另一套規則。
- 一律使用狗的時鐘和設定的時區（spec §13 已有此規定），並處理夏令時間。

## 4. 事件驅動：專業做法

### 4.1 事件來源分層

| 來源 | 例子 | 所需 License |
| --- | --- | --- |
| AI 感知 | 人員、入侵（圍欄內出現人）、跌倒、煙霧/火焰、遺留物、門未關、熱像異常 | `ai` |
| 系統 | 低電量、圍欄越界、E-Stop 解除、連線恢復、任務失敗 | — |
| 感測器 / plugin | 氣體超標、噪音超標、儀表異常 | 對應 plugin |
| 外部整合 | 門禁告警、消防盤、手動派遣按鈕（經 Gateway webhook / MQTT） | `mission` |

沒有 `ai` License 的狗：AI 類觸發在編輯器裡顯示為鎖定並寫明原因，不要隱藏（和 spec §2 的原則一致）。

### 4.2 AI 事件一定要有「防誤報」設計
AI 一定會誤判。如果每次偵測都直接觸發動作，狗會整晚亂跑、亂廣播。建議預設開啟以下幾層：
1. **信心門檻**：`minConfidence ≥ 0.8`
2. **持續時間**：人員要連續出現 3–5 秒才算，濾掉只閃一下的誤判
3. **次數條件**：例如 60 秒內出現 3 次
4. **區域過濾**：只在限制區、夜間時段生效
5. **去重**：同一個追蹤 ID 或同一區域在冷卻時間內只觸發一次
6. **確認模式**（見 4.4）

### 4.3 事件回應要能「去事件發生的地方」
事件帶有位置。事件回應任務的目標應該是 `EventLocation`：狗規劃路徑到事件位置附近，轉頭看過去，然後執行動作（快照、熱像、開通話、廣播）。這是事件驅動和時間驅動最大的差別，也是固定路線做不到的事。

### 4.4 三種執行模式（human-in-the-loop）

| 模式 | 行為 | 適合的情境 |
| --- | --- | --- |
| `auto` | 直接執行 | 低風險、高信心（例如：門未關 → 過去拍照） |
| `confirm` | 推送到在線手機：「南走廊偵測到人員（0.87）· 要派狗過去嗎？」逾時後依設定自動執行或取消 | 會對現場有影響的動作（廣播、靠近人員） |
| `notify` | 只通知、記錄，不動 | 調整參數期間、低信心事件 |

⚠ 本產品**沒有雲端**：通知只能送到區網內在線的手機。如果都沒有手機在線，`confirm` 要依 `onTimeout` 處理，這一點要在 UI 上寫清楚。

## 5. 仲裁：一隻狗、很多規則時怎麼辦（最容易被忽略的部分）

一隻狗同一時間只能做一件事。規則一多，一定會撞在一起。

### 5.1 優先級與搶佔
```
P0 緊急        火災、跌倒、入侵確認      → 可以打斷任何任務
P1 事件回應    AI 人員、門未關、氣體超標  → 可以打斷 P2、P3
P2 例行巡邏    時間排程                  → 不打斷別人，只排隊
P3 維護        回充、校正、地圖更新
```
- 被打斷的任務依 `onPreempted` 處理：**resume**（從中斷的航點繼續，建議預設）、restart 或 drop。
- **手動操控永遠最優先**：規則不能從操作員手上搶走操控權，只能發通知「有 P1 事件等待處理」。

### 5.2 排隊與過期
- 忙碌時新觸發的任務進入佇列，依優先級排序。
- 事件回應有時效性，要設 `queueTtlSec`，例如 5 分鐘後就從佇列移除並記錄「逾時未處理」，不要半小時後才跑去看。

### 5.3 啟動前的守衛條件
每次啟動前都要檢查：電量足夠（依任務估算再加上安全餘量）、狗的狀態允許（不在 E-Stop、故障、手動操控中）、License 有開、不在例外日內。不成立時要記錄原因，不能靜默失敗。

### 5.4 節流
`cooldownSec`、`maxPerHour`：避免同一條規則在短時間內反覆觸發，把電量耗光。

## 6. 後續動作與升級（第二階段）

- **串接**：A 任務成功 → 觸發 B；失敗 → 觸發 C。
- **升級**：事件回應完成後，如果人員**仍然存在**超過 60 秒 → 升級為 P0（例如開啟雙向通話、狗端警示燈、推播所有在線手機）。
- 建議做成有限狀態，而不是任意的流程圖，才能驗證、不會產生無窮迴圈。

---

## 7. 可觀測性：讓人知道「為什麼跑、為什麼沒跑」

1. **每次執行都記錄原因**：「因為 AI 偵測到人員 @南走廊（信心 0.87）觸發 · 由 夜班 · Pixel 8 確認」。
2. **「為什麼沒跑」**：規則詳情顯示最近 N 次被擋下的原因（冷卻中、電量不足、被更高優先級佔用、信心不足）。這是調整規則時最需要的資訊。
3. **未來 24 小時行程**：時間軸顯示接下來會跑什麼、哪裡會衝突、哪裡電量不夠。
4. **測試觸發**：在規則頁按下「模擬事件」，實際走一遍決策流程，但不讓狗真的移動（dry-run）。

---

## 8. 規則由狗端執行，手機只是編輯器

和 spec §8 一致：規則存在並在 Gateway 上評估，手機離線時規則照樣運作。手機負責建立、編輯規則、接收確認請求、查看紀錄。

## 9. UI 建議

- 任務 tab 分成三個子分頁：**任務範本** ｜ **自動化規則** ｜ **行程**（未來 24 小時時間軸）
- 規則編輯器用自然語句的結構：

  > **當** [AI 偵測到人員] **在** [南走廊、機房] **且** [夜間 22:00–06:00、信心 ≥ 0.8、持續 3 秒]
  > **就** [派狗前往事件位置 · 拍照 · 詢問操作員] **優先級** [P1 事件回應] **冷卻** [5 分鐘]

- 事件回應提供範本：「前往查看」「驅離廣播」「開啟通話」「繞區巡查」，大部分情境不需要從零開始建立。
- 確認請求用和「有手機請求加入」相同的推播式對話框，上面顯示倒數計時與快照縮圖。

## 10. 建議的實作分期

**第一期（Mock，約 3–4 天）**
- Mission / Rule 拆開（保留向後相容：舊的 `Mission.trigger` 自動轉成一條 Rule）
- 時間觸發：RRULE（每日、每週、時段 + 間隔）、隨機偏移、錯過的排程規則
- AI / 系統事件觸發：區域、信心、持續時間、冷卻、去重
- 優先級、搶佔、佇列 TTL、守衛條件
- `auto` / `confirm` / `notify` 三種模式，確認對話框
- 執行紀錄的「原因」欄位，以及「為什麼沒跑」
- 「未來 24 小時行程」視圖
- 前往事件位置（`EventLocation`）的任務目標

**第二期**
- 串接與升級、外部整合（webhook / MQTT）、例外日曆、dry-run 模擬、依區域的巡邏覆蓋率報表
